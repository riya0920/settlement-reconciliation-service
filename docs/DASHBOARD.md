# SE-2 — the operator dashboard

Generated by `run_dashboard.py` from a real settled book: 1,500 internal
transactions, real reconciliation, 40 real chargebacks. The rendered
page is `docs/dashboard.html` and is served live at `/dashboard`.

`README.md` listed this as open: *the API returns the numbers; nothing
renders them, and there is no alert rule on aged breaks or fee
variance*.

## The design constraint: thresholds are imported, never re-typed

| what the page colours red | where the number comes from |
|---|---|
| break tiers | `break_queue.TIERS` via `tier_for()` |
| fee materiality | `dispute_pack.DEFAULT_MATERIALITY_MINOR` |
| evidence windows | `chargebacks.EVIDENCE_WINDOW_DAYS` |
| worth defending | `chargebacks.WINNABLE` |

This is the one a dashboard usually gets wrong. Someone tunes a
threshold in the code, the dashboard keeps the old one, and for months
the screen and the system disagree about what is wrong — **and the
screen wins, because the screen is what people look at.** A dashboard
with its own copy of the rules is a second implementation of them.

A test asserts the imports are present AND that no tier boundary
appears as a literal anywhere in the module; another moves a boundary
at runtime and checks the alert moves with it.

## What it shows, and what it deliberately does not

| | |
|---|---|
| **pages** | **3** |
| alerts total | 4 |
| open breaks | 625 |
| open disputes | 40 |

### Needs action

| severity | rule | detail | action |
|---|---|---|---|
| **page** | `break_aging_t3` | 625 break(s) at T3 (10+ days) | controller review / write-off decision |
| **page** | `evidence_overdue` | 10 dispute(s) past their evidence deadline | already lost -- confirm and record, do not submit |
| **page** | `evidence_due_today` | 2 dispute(s) with the window closing today | submit today or the funds are gone regardless of merit |
| **ticket** | `evidence_due_soon` | 9 dispute(s) due within 2 days | assemble evidence now |

**Totals are not actionable.** *625 open breaks* tells nobody what to
do; *625 break(s) at T3* is a morning's work with a name on it.

### A silent zero, and what it hid

This ran once showing **625 open breaks** and **no break alerts at
all** on the same screen. The dashboard read `age_days` and
`break_type`; `Service.aged_breaks` returns `age` and `state`. Every
break — some **34 days old** — defaulted to age 0, landed in T0, and
raised nothing.

A missing age must not read as NEW. Zero is the one value that means
*everything is fine*, so it is the one value a missing field must
never become. `_age_of` now accepts both names and **raises** when
neither is present, and a test asserts it raises rather than
defaulting. The break TYPE still defaults to empty, and that is safe
in a way the age is not — an unknown type misses the ledger fast-path
and ages normally, where an unknown age silently ages nothing.

**Every alert carries an action**, taken from the tier that raised it,
so the row says what to do rather than only that something is wrong.
An alert with no action is noise, and noise is what an operator learns
to scroll past.

### Break tiers, as the queue defines them

| tier | from | action |
|---|---|---|
| T0 | 0+ days | monitor |
| T1 | 2+ days | assign to an analyst |
| T2 | 5+ days | escalate to the team lead |
| T3 | 10+ days | controller review / write-off decision |

Ledger breaks start at **T3** regardless of age — `break_queue` says
so and the dashboard inherits it by calling `tier_for` rather than
bucketing on age itself.

### Evidence deadlines beat amounts

Ordered by deadline, matching `representment.work_queue`: a $200
dispute due tomorrow outranks a $2,000 one due in three weeks, because
the second can still be fought and the first cannot. Sorting a work
queue by value is the intuitive thing and it loses the winnable
disputes at the front.

## Why it renders server-side to one file

No CDN, no build step, no JavaScript framework, no external fetch of
any kind — a test asserts the page contains no `http://`, `https://`,
`<script` or `cdn.`.

A settlement dashboard is looked at during an incident, and an
incident is exactly when a page that fetches a chart library from the
internet does not load. The page is also theme-aware and every value
is HTML-escaped, because a break reference comes from a settlement
file and a settlement file is input from outside.

`/dashboard.json` returns the same view as data, because **an alert
that only exists on a screen requires somebody to be looking at the
screen.** That is the endpoint a monitoring system scrapes.

## What this still is not

- **Nothing pages anybody.** `/dashboard.json` is scrapeable and
  nothing scrapes it. SE-3 has the Prometheus and Alertmanager path;
  this project has the rules and not the delivery.
- **No history.** Every number is as-of. *Is this worse than
  yesterday* is the second question an operator asks and this cannot
  answer it — that needs the figures stored per run, which is a
  different job from rendering them.
- **No drill-down.** The rows name a reference; following it means
  calling `/transactions/{ref}` by hand. DATA-1 carries provenance as
  columns precisely so the drill-down is a `WHERE` clause, and this
  page does not use it.
- **One book, one operator.** No per-desk filtering, no assignment, no
  acknowledgement. An alert nobody has claimed is one everybody
  assumes somebody else has.
