# SE-2 — the retention policy, executed

Generated by `run_retention.py` over a book of 3,300 settled
transactions across 11 business dates spanning eight years, so every
tier boundary is crossed by real data rather than asserted.

| policy | days |
|---|---|
| hot (indexed, queried daily) | 45 |
| archive (compressed, retrievable) | 545 |
| legal floor (minimum time to KEEP) | 2,555 |

## 1. Dry run — what it would do, before it does it

| | |
|---|---|
| dates it would archive | 6 |
| rows it would move | 1,800 |
| dates eligible to purge | 2 |
| rows still hot afterwards | 3,300 |

A job that deletes should be able to say what it would do first. The
hot count above is unchanged, which is the point of printing it.

## 2. The archival pass

| | |
|---|---|
| dates archived | 6 |
| rows moved | 1,800 |
| rows remaining hot | 1,500 |
| uncompressed | 542,538 bytes |
| gzipped archive | 34,144 bytes |
| compression | **15.9x** |
| wall clock | 1.37s |

The hot store went from 3,300 rows to 1,500 — a 55% reduction — and
nothing was lost, because every archive file was read back and its row
count checked **before** the hot copy was deleted. Any other order has
a window where a crash loses the data, and "we archived it" with
nothing at the other end is worse than not archiving.

## 3. Running it again

| | first run | second run |
|---|---|---|
| dates archived | 6 | 0 |
| rows moved | 1,800 | 0 |
| skipped, already archived | 0 | 6 |

It runs daily and will be re-run after failures. The dangerous version
of non-idempotency here is not a duplicate file — it is that the hot
rows are already gone, so a second unguarded pass would write an
**empty archive over a good one**.

Getting this right required a fix that is worth stating plainly: the
job's date list originally came from hot storage alone, so it forgot a
date the moment it archived it. Nothing already archived could be
reported as already archived, and — far worse — nothing already
archived could ever be **purged**, because the purge branch only ever
saw dates still sitting hot. The list is now the union of both tiers.

## 4. A dispute arrives for archived data

The reason the archive exists. A chargeback carries a reference and no
idea which tier the data is in, so the lookup covers both and says
which one answered.

| reference | tier | business date | amount | provenance | lookup |
|---|---|---|---|---|---|
| `20260823-0100` | **hot** | 2026-08-23 | 14,700 | STL20260823 line 100 rule `exact_ref` | 0.000s |
| `20200128-0100` | **archive** | 2020-01-28 | 14,700 | STL20200128 line 100 rule `exact_ref` | 0.037s |

Both answers are evidence. The archived one took 96x longer to
find, which is the trade the tier exists to make — the archive is
deliberately unindexed, because indexing it would cost most of what
archiving saved. An hour to answer a dispute is acceptable; losing the
dispute is not.

Note what travels with the row. Archiving the amount alone would keep
the half a representment does not need and lose the half it does:
**which file said so, on which line, under which rule.**

## 5. Purge — a different verb, and a separate flag

| | |
|---|---|
| dates past the legal floor | 2 |
| purged by the runs above | 0 |

Zero, because `purge` defaults to off. Archiving is reversible and
purging is not, so they are two verbs taking two flags. A single
`run_retention()` that quietly deletes past the floor is how a routine
job becomes an incident.

A second thing this run made explicit, and it cost two failing tests to
find: **a purgeable date is never archived on the way past the floor.**
Archiving data you are already permitted to delete buys nothing, so it
is left where it is and marked eligible — which means purge has to
reach into *hot* storage, not only into the archive. A purge that
deletes only archive files would leave those rows in place while
logging a deletion that did not fully happen.

Run with the flag:

| business date | rows | bytes | reason |
|---|---|---|---|
| 2018-06-07 | 300 | 0 | past legal retention floor (hot, never archived) |
| 2019-07-12 | 300 | 0 | past legal retention floor (hot, never archived) |

The purge log is the part people skip. Deleting data without recording
that you deleted it turns a defensible policy into an unexplainable
hole — an auditor asking what happened to a record needs a better
answer than "we have no idea".

## 6. Is every date accounted for?

The question an auditor asks is not *what is your policy* but *where is
the data for 14 March*.

| tier | dates |
|---|---|
| hot | 3 |
| archived | 6 |
| purged, on record | 2 |
| **total accounted** | **11** of 11 |

No date appears in two tiers, and none is missing from all three. A
date that is neither hot nor archived nor in the purge log is an
unexplained hole, and this is the check that finds one.

## 7. Is the policy long enough?

Retention derived from a storage budget is a decision to lose winnable
disputes. Derived from the observed dispute-age distribution, it is a
control. `RetentionPolicy.validate_against` checks one against the
other:

| observed max dispute age | verdict |
|---|---|
| 120 days | archive window covers the observed dispute tail (margin +425 days) |
| 540 days | archive window covers the observed dispute tail (margin +5 days) |
| 700 days | ARCHIVE WINDOW IS SHORTER THAN OBSERVED DISPUTES -- evidence will be missing when it is needed (margin -155 days) |

The third row is the one to look at. An archive window shorter than the
observed dispute tail means evidence will be missing exactly when it is
needed, and the policy will look fine on every metric until the first
dispute that reaches past it.
